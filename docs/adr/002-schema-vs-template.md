# ADR-002：Schema 只管模型，布局权力交还 Template

- **状态**：Accepted
- **日期**：2026-08-12
- **来源**：动态表单架构设计推演

## 背景

传统 `ElForm + ElFormItem + Row/Col + Input` 样板重复，催生「动态表单 / Schema 驱动」。主流方案（Formily、各类 JSON Schema Form 等）常走向极端：在 JSON 里同时描述字段、布局、联动，甚至发明 Void 虚节点做卡片/行列。

现实痛点是：

- 身份证号默认在中间；个别场景要前置并加「联网查询」回填——纯配置里写这类临场交互往往比手写 Template 更难懂
- 同一领域模型在 User 页与 Order 页布局不同，需要共享 + 覆盖，而不是复制整份 Schema
- 「配置 ↔ 模板」无痛切换：先配置后改布局、模板里嵌一小段配置，多数方案未想清楚

## 决策

**只配置稳定的模型（字段 ↔ 默认控件 / 元数据），不配置复杂布局 DSL。**

- 标准顺序排布：可提供「按 schema 顺序渲染」的便捷路径（渐进退化）
- 需要定制：在 Template 里显式摆放字段组件、改 `span`、插槽注入按钮/联动
- 允许在布局容器内混写原生表单项，作为逃生舱

公式心智：

```text
配置（View-Model） + Template（排版） ≫ 完整 JSON 布局引擎
```

常见栅格、间距、显隐等可逐步「带到 layout」做成轻量配置（减少重复），但**不以运行时 JSON 吞掉全部排版与交互**。页级默认与字段覆盖的优先级、以及不自研 Row/Col，见 [ADR-007](./007-layout-adapter-and-span-priority.md)；Schema 应尽量避免成为布局 span 的主来源。

## 备选方案

1. **全量 Schema 驱动（含布局节点）**：复用极高，但 DSL 晦涩；复杂交互被迫写 render / 自定义组件，配置复杂度常超过 Template。
2. **纯手写 Template**：灵活性最高，样板与重复绑定最多，领域模型难以单点复用。
3. **仅 `items` 数组 + 单一 `DynamicForm`**：显示隐藏进 setup，template 几乎空壳——边界倒置，布局仍不自由。

## 后果

- **正向**：心智回到「写 Vue」；避开 Void/布局 DSL；配置与模板可渐进切换。
- **代价**：放弃「一份 JSON 跑所有页面」的幻觉；可视化设计需面向「生成模型 + 布局模板」而非单一巨型 Schema（见 ADR-006）。
- **关联**：字段在模板中的表达见 ADR-003；布局容器见 ADR-004；栅格适配与 span 优先级见 ADR-007。
