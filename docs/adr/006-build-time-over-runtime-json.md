# ADR-006：编译时低代码 / GitOps 优先于运行时 JSON 下发

- **状态**：Accepted
- **日期**：2026-08-12
- **来源**：动态表单架构设计推演

## 背景

「动态加字段」常被默认理解成：**后端下发 JSON，前端运行时解析渲染**。在企业中后台里，这经常是伪需求：

- 加「工作电话」通常伴随 DB 列、DTO、接口、导出/报表变更——后端本就要发版，却单独要求前端零发版，逻辑矛盾
- 运行时引擎换来的是类型丢失、调试困难、布局 DSL 膨胀（与 ADR-002 冲突）

真需求大致限于：SaaS 多租户自定义扩展字段、运营侧秒级生效的问卷/活动、超复杂审批权限矩阵等。

另一条路：**可视化配置 → 生成代码 → Git Commit → CI/CD 构建部署**（Build-time Low-Code / GitOps）。

与本库目标形态（静态 `createFormControls` + Template 布局）天然契合：生成物是普通的控件表 / `UserForm.vue`，AST 友好、可手工接管。

## 决策

1. **vue-formless 默认面向编译期 / 源码期复用**，不以「通用运行时 Schema 渲染器」为第一目标。
2. **布局配置**可以存在（栅格、间距、显隐等），优先作为**源码或生成代码中的声明**，而非必须由后台页面运行时下发。
3. **仅在明确的真需求场景**再引入运行时 JSON 子集（扩展字段、权限可见性等），并与静态 Fields 组合，而不是替换整套架构。
4. 若提供可视化工具，输出应对齐 ADR-003/004 的代码形态，保证程序员可读、可 PR、可 `git revert`。

## 备选方案

1. **运行时全量 JSON 引擎**：多租户/秒级运营场景有价值；代价是类型、性能、DX 与布局 DSL。不作为默认。
2. **纯手工维护模型与模板**：无生成管线时的常态；与 ADR 不冲突，可视化是增强而非前提。
3. **后台改配置触发前端自动改代码并部署**：与本决策一致，属工程配套，不必塞进运行时内核。

## 后果

- **正向**：保留 TS/Volar/断点调试；审计与回滚走 Git；运行时零解析器税；与「Schema 只管模型」一致。
- **代价**：非多租户场景下，「运营改完立即全网生效」不是默认能力；真要秒级生效需另建运行时通道。
- **关联**：分层与 API 形态见 ADR-001～005。
